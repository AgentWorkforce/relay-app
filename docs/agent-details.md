# Agent details data contract

The Agents page reads `roster.list` through the signed-in desktop core. A roster row has `name`, `address`, `kind`, `where`, `status`, `last_seen_ms`, `description`, `host`, `owner_hash`, `is_self`, and, while the agent is live, `activity`. The core intentionally reduces the Relaycast record; arbitrary registration metadata is not passed to the UI. The list is already refreshed by the page. The expanded view uses these fields without adding one network request per open row.

The one-line summary uses the agent's `activity` while it runs, then a short agent summary if a future authorized core contract supplies one, then recent outgoing text if supplied, then the existing description. Spawn-instruction boilerplate is suppressed. When no task text is available, the page says so instead of presenting a brief path as current activity. Idle workers show idle time when their last activity is known.

Per-agent outgoing messages, PR mentions, transcript links, and terminal event streams are not present in `roster.list`. The desktop's `messages.history` is the signed-in person's one-to-one conversation with an endpoint, and `activity.list` describes deliveries to local agents; neither is a general history of what another agent sent. Agent Relay exposes workspace message search, while hosted shared sessions and RelayHistory hold other possible activity evidence. A follow-up core API should return a bounded, authorized per-agent view and capability links. It must enforce the signed-in person's access to private DMs and transcripts before the UI renders them. A short live status is now derived rather than set by the agent: roster rows carry `activity` (working or idle, repo@branch, and the session title with its to-do list's item in progress) with its update time, shown only while the agent is live; see [What an agent is doing](agents-people.md#what-an-agent-is-doing). The spawn task must not stand in for live status.

Local session registrations already publish `cloud_user_id`, `cloud_workspace_id`, and `owner_hash` from the signed-in account. Spawned workers publish declared organization, project, workstream, role, and objective, but no owner identity. The desktop therefore leaves many spawned workers in **Other live agents**. Cloud node enrollment has a `createdBy` user ID, but the roster has no node ID. [AgentWorkforce/relay#1895](https://github.com/AgentWorkforce/relay/issues/1895) tracks publishing the workspace-scoped owner identity from trusted enrollment and spawn paths. Ownership should be fixed at that source and published as the same owner metadata as local sessions. A future app fallback would require an authenticated node-to-person mapping supplied by the core; a matching host or workspace alone is insufficient proof of ownership.
