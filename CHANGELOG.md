# Changelog

Write the user-facing changes for each release under `## Unreleased` before
running the Desktop Release workflow. The workflow copies that section into
**What's new in this release** and uploads a promoted changelog artifact after
publishing. Right after the publish, the maintainers download that
artifact (it expires after 30 days; past that, or when a publish uploaded none,
the same section is taken from `CHANGELOG.md` at the `released-v<version>`
commit, whose `## Unreleased` bullets are what shipped) and lands it on `main`
through the maintainers' review flow, merging rather than
replacing: the released bullets move under the version heading, and bullets
that reached `## Unreleased` after the released commit stay there. A release
whose `## Unreleased` section has no bullet stops before building.

## Unreleased

- **A Connect room you left open stays open after a restart.** On macOS, Linux and Windows, when Agent Relay starts more than 15 minutes after a joined Connect room's saved end time, it now asks Agent Relay Cloud whether the host extended the room before closing it, instead of dropping you from a room that is still open. Handoffs nobody accepted are still cancelled at startup, and the room closes with the usual notice when Cloud says it is over or cannot be reached.
- **Fork an agent's session from your phone.** On iPhone and iPad, a Claude or Codex agent's detail view has a fork button that starts a new agent on the same computer, in the same folder, with a copy of the whole conversation, while the original keeps running. Only the computer's owner can fork its sessions; a computer on an older Agent Relay is shown as unable to fork until it is updated. If the reply to a fork never arrives, the app stops and asks you to check Agents instead of starting a second one.
- **The iPhone and iPad app says it is loading instead of showing an empty list.** On iOS, until the first agent list answers after launch, the Agents and Messages lists now say "Loading…" rather than "No agents in this view", which read as an empty workspace on a slow connection. The app also logs its startup steps and their timings (no account, workspace or message data) under the `startup` category in Console.app and Instruments.
- **The iPhone sign-in screen and sheets fit the screen.** On iOS, the sign-in screen (logo, title and text) was laid out 380 points wide plus margins, wider than any iPhone, so it ran past the screen edges; Settings, New message and New agent also kept their iPad minimum width on iPhone. They now fit the iPhone screen; iPad is unchanged.
- **Agent Relay no longer asks to reload Codex chats at every launch.** On macOS, Linux and Windows, Agent Relay no longer shows “Reload Codex chats” for Codex right after it starts. Chats that were open before Agent Relay was set up, once another chat shows the tools working, a Codex daemon that is slow to answer, or chats still starting the tools after a reload now leave the provider at “Setup saved”, and Agent Relay checks again shortly; Connection details say how many older chats still need a reload. Check connection still reports every chat that has not loaded the tools.
- **WSL sessions show up at sign-in on Windows.** On Windows, the sign-in preview now lists sessions inside running WSL distributions too; it used to miss them because it ended before the distributions were looked at. WSL folders you add yourself, in Settings or `AGENT_RELAY_CLAUDE_CONFIG_DIRS`, are now always read when they can be, even while their distribution is not listed as running or with `AGENT_RELAY_WSL_HISTORY=0`; a folder named this way may start its stopped distribution. The background collector no longer logs, every minute, the private WSL home folders of other users that it may not open. On Linux and Windows, the sign-in preview now re-reads local history, as it already does on macOS, so a first sign-in lists sessions.

## v2026.11.6

- **Spawned agents take your messages, and their spawning agent's, as their own input.** On macOS, Linux and Windows, a direct message from you (desktop app or phone) or from the agent that spawned a headless session now reaches spawned Grok, Devin and OpenCode agents as native input on their own prompt channel, with the reply command kept, instead of as a peer message; Codex and Claude already did. A reply inside the DM thread, and a DM picked up after the computer slept or reconnected, now count as direct messages too; they used to arrive as peer messages, even in Codex and Claude. Spawned Muse agents are unchanged: Muse offers no input channel for this, so their spawning agent's messages keep the owner framing. Approvals still belong to you, in Codex and Claude only.
- **New license: FSL-1.1-ALv2.** On macOS, Linux and Windows, starting with this release Agent Relay is licensed under the Functional Source License, Version 1.1, ALv2 Future License instead of Apache-2.0: use and modify it freely, but don't offer it as a competing product or service; each release becomes Apache-2.0 two years after it ships. Earlier releases stay Apache-2.0. The bundled LICENSE file and the macOS About copyright line change accordingly; see NOTICE.
- **Upload status recovers after a slow disk instead of staying on Preparing.** On macOS, Linux and Windows, when reading upload status from a large session history takes longer than its 15-second limit, Agent Relay now keeps that one read going and gives its answer to the next refresh, instead of starting another read beside it each time. A busy or nearly full disk no longer leaves Settings showing "Preparing" long after the history is ready.
- **Claude Code checks what teammates are working on.** On macOS, Linux and Windows, Agent Relay adds a Claude Code session-start hook, with its hosted MCP setup, that asks each new session to read teammates' short session summaries before starting work, open the full summary only when one looks related, and message the teammate instead of duplicating their work. It is off by default until session summaries are available; tick *Have agents check what teammates are working on* in the first-run provider chooser, or turn it on in Settings › Providers › Claude Code. Codex is not covered yet.
- **Sessions inside WSL are shared on Windows.** Agent Relay now also reads Claude Code, Codex, Copilot and other agents' history kept inside a running WSL distribution (`/home/<user>`), with the same sharing settings as the rest. Stopped distributions are left alone, and `AGENT_RELAY_WSL_HISTORY=0` turns this off.
- **Branded builds no longer show their profile id.** On macOS, Linux and Windows, a build named for its own product (a customer's branded build) no longer shows its profile id beside its name in the menu bar or tray, window title and header. Settings › About still shows it. Agent Relay Dev and other builds named Agent Relay keep their badge.
- **New animated session avatars.** On macOS, Linux and Windows, sessions that show an animated profile shape now use Agent Relay's own artwork: the same shapes and colours, drawn fresh, with a gentle breathing motion. Reduce Motion still keeps them still.

## v2026.11.5

- **Uploads no longer stop on sites without direct uploads.** On macOS, Linux and Windows, 2026.11.4 asked the site for direct-upload credentials and, when the site had no such route (agentrelay.com today), stopped every upload with "Upload stopped". Agent Relay now treats that answer as direct uploads being off and sends sessions the usual way; uploads stopped by it resume on their own after updating.
- **Session bodies are scrubbed with relayscrubber 0.5.0-alpha.8.** On macOS, Linux and Windows the scrub engine moves from 0.5.0-alpha.5 to 0.5.0-alpha.8 (still ruleset 10), which redacts bare credential assignments such as `password = value;` that alpha.5 passed through. Versions alpha.6 and alpha.7 were never shipped.
- **Upload choices survive policy changes.** On macOS, Linux and Windows, sessions you turn off stay excluded when switching to automatic uploads. Only new sessions keeps existing sessions local, while All removes automatic baselines without clearing individual denials. Exclusions from older builds are kept conservatively until you explicitly enable those sessions.
- **A site build can name private storage hosts for direct uploads.** On macOS, Linux and Windows, a site profile's `DESKTOP_HISTORY_UPLOAD_STORAGE_ORIGINS` lists the https origins of its storage (a MinIO store on the organization's private network, say), and direct uploads may PUT to them even when they resolve to private addresses. Only a PUT to an exactly listed scheme, host and port gets through; every other History request keeps refusing private addresses, and Agent Relay's own builds are unchanged.

## v2026.11.4

- **Installing a new version by hand no longer leaves the old one uploading.** On macOS, Linux and Windows, the background session collector stops by itself when its program is replaced on disk or when your saved sharing choice no longer matches the one it started with, and the new build takes over with your current choice, so a session you keep local stays local. On macOS (launchd) and Linux (the `agent-relay.service` unit) the background service also restarts into the new build; on Windows it keeps running until the app restarts it. If the service still runs another build (on macOS, after a few restart attempts), the app says so and asks you to quit and reopen Agent Relay. The app no longer shows **Only sessions I choose** when it can't confirm which sessions the collector shares; it shows the upload service needs attention.
- **Uploads name the organization policy they were made under.** On macOS, Linux and Windows, every History upload and every direct-upload credentials request sends the operator policy revision this computer applies (`X-Agent-Relay-Capture-Policy-Revision`), when one has been read. A server that enforces the policy refuses an upload made under an older policy with 409 `capture_policy_stale`; the batch is retried, and goes through once the next policy read applies the current revision.
- **Self-hosted sites whose storage issues presigned upload URLs get direct uploads too.** On macOS, Linux and Windows alike, when the site's storage has no session credentials (a MinIO store, say), Desktop asks Control for a presigned URL for each batch's object and stores the batch there, with the same pending, queued and set-aside handling as other direct uploads; storage that encrypts on its own needs no KMS key. Presigned URLs are kept in memory only, and a batch the pipeline refuses because it was stored unencrypted is set aside as receiver_rejected.
- **Agents can create a channel on the relay.** On macOS, Linux and Windows, the bundled core takes `agent-relay-probe relay subscribe-channel <channel> --create [--topic <topic>]`: it creates the channel when it does not exist (`POST /channels` on the session socket) and joins it; an existing channel is joined as before. Spawned service callers also replay their invokes durably and require the server's replay-resume proof (relay 18.1.0).
- **History uploads go straight to your workspace's storage when Control offers it.** On macOS, Linux and Windows, a session batch is stored as one object in the workspace's upload inbox with short-lived credentials from Control, and the batch stays pending until the pipeline admits it, then counts as queued; a pending batch is asked about again on later passes and after a restart without being stored twice. A batch the pipeline refuses is set aside (blocked) as receiver_rejected, like one History rejects, and is not posted to History. When Control does not offer direct uploads, or cannot answer, batches are posted to History as before. The upload credentials are kept in memory only and asked for again after a restart.
- **Sign-in names the site's OIDC provider whenever the site publishes one.** On macOS, Linux and Windows, the sign-in screen and its methods line now name the OIDC provider also on a site that offers password or email-link sign-in, instead of only when OIDC was the sole method.
- **Sign in with Microsoft on a self-host site.** On macOS, Linux and Windows, when the site has Microsoft sign-in configured, the sign-in screen offers **Continue with <its name>** above **Continue in browser**, and the methods line names it.
- **Registered agent names are recorded in session history, so @agent search can find a session by the name it has on the relay.** Desktop now hands each registered session's name (the alias once renamed) to local history before every delivery pass, and history records it.
- A scrubber upgrade that changes a queued upload now saves it under a new batch ID before sending. Retries keep the saved bytes and batch ID together, including after a restart or a lost acknowledgment.
- **A marked direct message to you raises a desktop notification.** On macOS, Linux and Windows, a direct message to your own identity that carries a `relay_alert` marker (a title and an https link) shows one notification with the title, a short preview and the link; messages from agents, unmarked messages and self-messages never do, and a sender is limited to three alerts per ten minutes. A spawned agent's session now binds to its spawn registration instead of registering a second identity.
- **A local certificate override is reported even while the workspace History name does not resolve.** On macOS, Linux and Windows, a nonempty `SSL_CERT_FILE` or `SSL_CERT_DIR` is now reported, and History uploads take the one-minute local wait, while a self-hosted History name fails to resolve, instead of retrying with DNS backoff and showing History as unreachable until DNS recovers.
- **Session bodies are scrubbed with relayscrubber 0.5.0-alpha.5 before they are stored or uploaded.** On macOS, Linux and Windows, the scrub seam now runs the relayscrubber crate (ruleset 10) instead of passing bodies through unchanged. Credentials such as API keys, tokens, passwords and signed URLs are replaced with `[REDACTED]` in session content before it is stored locally or sent to History. This early version also hides some ordinary text that only looks like a credential, such as code that names a token variable; later versions narrow that. alpha.5 closes leaks alpha.4 still had.
- **A new build of the same version replaces the running uploader and the command-line probe.** On macOS, Linux and Windows, installing another build of the version already installed now restarts the history uploader on the new build and refreshes the installed `agent-relay-probe`, instead of leaving the previous build's running. A site profile built to coexist with Agent Relay on macOS leaves Agent Relay's history uploader and `agent-relay-probe` alone when both are the same version.
- **Session bodies pass through a scrub seam before they are stored or uploaded.** On macOS, Linux and Windows, session content queued for upload, sent to History or downloaded from a remote source now passes through a scrub seam first; scrubbing itself arrives with the relayscrubber crate. A body the engine refuses is never stored or sent raw: queueing it is rolled back, or its batch is not sent, and the upload is blocked as an invalid payload until you press **Retry** or a new build starts for the first time. Nothing retries it on its own. A refused download is reported as failed.
- Sign-in shows the self-host site's logo, organisation name and allowed sign-in methods from its login configuration, with the logo only from a public host name; an expired sign-in after a password reset asks you to sign in again (macOS and GTK).
- **History uploads resume after clearing a certificate-file override.** On macOS, Linux and Windows, local certificate configuration refusals, including the pre-upload destination check, keep queued uploads retryable with a fixed one-minute wait. Clearing the override and restarting no longer leaves those jobs permanently blocked; pressing **Retry** preserves the queued batch. Jobs already blocked by an earlier build still need **Retry**. Unsafe destinations remain blocked even with an override set, and receiver permission refusals remain blocked too.
- **Retry acts at once after a local certificate configuration refusal.** On macOS, Linux and Windows, pressing **Retry** on a History upload waiting out the one-minute wait after a local `SSL_CERT_FILE` or `SSL_CERT_DIR` refusal now tries it straight away instead of after the minute.
- **Self-hosted connections use the operating system's certificate trust.** On macOS, Linux and Windows, sign-in, Relaycast, History and optional collector analytics use platform certificates with strict hostname checks. A nonempty `SSL_CERT_FILE` or `SSL_CERT_DIR` refuses new History and analytics connections, even to public-CA sites; unset both and install your site's CA in the operating system trust store. Collector batches refused locally for these overrides are dropped without retry backoff. History replaces its HTTP connection pools when the shared platform trust snapshot refreshes. A macOS site build registers only its own connection link scheme.
- **Site profiles keep their own Relay socket and hooks.** On macOS, Linux and Windows, a coexisting site build no longer rewrites Agent Relay’s socket pointer or replaces its Claude Code session hook. Each build repairs only its own pointer and enabled hooks. Profiles leave integrations that have one shared configuration file alone.
- **Initial setup omits uninstalled Amp and Capy.** On macOS, Linux and Windows, uninstalled Amp and Capy no longer appear in the initial provider chooser because of an old selection, Cloud connection or leftover Capy data. Existing connections, saved choices, session history and the explicit Add provider catalog are preserved.
- **The first history scan finishes much sooner.** The first history scan after sign-in or re-enrolment runs with a larger, bounded capture budget (at most one core, about half of one in each lane) and finishes much sooner; steady-state capture keeps its light footprint.
- **Linux:** an installer rollback now waits for a session history migration lock instead of giving up, and the installer no longer fails on older bash when no locks were taken.
- **Linux headless updates protect upgraded session history.** Install and rollback checks reject a core that cannot read the local upload format, including a fallback after a failed start. Saved evidence, queued uploads and the compatible recovery binary are retained; a matching version alone no longer counts as an up-to-date installation.
- **The Open button no longer keeps an outdated label after a failed session check.** On Linux and Windows, when Agent Relay can't verify how to open a session, the button returns to **Open session** instead of showing the wording from an earlier check.
- **Factory Droid can be set up with the hosted MCP server from the Providers list** (macOS, Linux; Windows detects the `droid` command on PATH only).
- **Factory Droid sessions appear in session history.** On macOS, Linux and Windows, Agent Relay now uses RelayHistory 0.58.0, which reads Factory's Droid CLI sessions from `~/.factory/sessions` and lists them as **Factory Droid** beside Claude Code, Codex, OpenCode and the other providers, subject to your session-sharing setting. New Factory Droid sessions are picked up as they are written.
- **A development build leaves the installed command-line probe alone.** On Linux and macOS, a from-source build of the core (version `…-dev+…`) no longer replaces `~/.local/bin/agent-relay-probe`, so running one beside the installed release cannot migrate the shared history database ahead of the release core.
- **Session-opening buttons show their provider icon and fill the Details panel.** On macOS, opening a session in its original app now uses the same full-width action layout as View on web and Refresh transcript. Linux and Windows now show the matching provider artwork and action wording, including after a refresh.
- **Service callers can poll a `spawn.release` to completion.** On macOS, Linux and Windows, the invocation a `spawn.release` answers with is now kept in the caller's ledger with the released worker, so a Flows caller's `spawn.status` on it reports the release instead of answering `not_in_ledger`. Other callers still cannot see it.
- **Deleting sessions from Cloud waits for the operator policy.** Deleting your sessions from Cloud now waits until your organization's upload policy has been read, like resuming uploads, and says so, instead of being allowed while the policy is unknown.
- **Relay messages wake an idle Cursor CLI session.** On macOS and Linux, an interactive Cursor CLI (`cursor-agent`) session waiting at its prompt now gets a relay message within seconds, as Cursor editor chats already did, instead of at its next tool call or prompt, and keeps doing so after several automatic follow-ups in a row. An idle Cursor editor chat is now also woken after a turn Cursor started itself, such as one reporting that a background task finished, and a Cursor editor chat can put itself on the relay during its first turn. Cursor sessions are told to reply through the session socket (with `agent-relay-probe` in the Cursor editor on macOS), never through hosted MCP tools, which cannot send as a Cursor chat. Windows still has no Cursor route.
- **A cloud reset no longer stops uploads for good on a history service that cannot reset.** On self-hosted installs whose history service does not support cloud reset, on macOS, Linux and Windows, a session reset now ends with "This history service does not support cloud reset. Uploads continue." and uploads resume, instead of staying stopped while the reset waited to be retried. A reset already waiting this way finishes the same way on the next start. When the history service says up front that it has no cloud reset, the reset is refused before anything is stopped.
- **A site profile can coexist with Agent Relay on macOS.** A site profile built with `DESKTOP_COEXIST` neither replaces an installed Agent Relay nor is replaced by it, and runs its own core beside it. Linux and Windows are unchanged, as they have no product takeover.
- **A profile build shows its own name and profile instead of the Agent Relay wordmark.** On macOS, Linux and Windows, a build made for a site profile shows its product name in text with its profile id beside it instead of the Agent Relay wordmark, adds the profile id to the window title, and marks its menu-bar or tray icon: on macOS the icon carries the profile id, and on Linux and Windows, where the tray icon is too small for text, it carries a dot and the item's title or tooltip names the profile. Settings › About shows the build's identity: its profile, app id, site host and core socket. On Linux and Windows, as on macOS, any build that differs from the default (including one with only another releases repository or feed) is marked, with its profile id or, without one, its asset prefix or "profile". Agent Relay itself looks as before.
- **A site profile build's Claude Code and Codex connections reach that build's own core.** On macOS, the Claude Code and Codex MCP sign-in helper and Claude Code's chat identity hook that a site profile build installs now name that build's own core instead of reaching the Agent Relay app's. On Linux and Windows, a core started on a socket other than the default does the same. The profile build keeps its own Claude Code and Codex entries (`agent-relay-<profile>`) and its own chat identity hook beside Agent Relay's, so the two apps on one computer no longer replace each other's. The Agent Relay app's own entries are unchanged.
- **About > Diagnostics names the core crates the app was built with.** On macOS, Linux and Windows, the Build section shows the agent-relay-node commit and the relaycast version the build's lockfiles resolved. Internal prepare-only builds can choose them through Desktop Release's `agent-relay-node-rev` and `relaycast-version` inputs, allowed only for a profile whose environment sets `DESKTOP_CRATE_OVERRIDES_ALLOWED` to `true`. relayscrubber gets an input when its crate lands; relayhistory and terse have none, because Desktop does not depend on them as crates.
- **History uploads go one batch at a time.** On Linux, macOS and Windows, history uploads now send one batch at a time per origin, with smaller batches during the first sync. When an upload is retried, the log names the cause. When local history is busy, status shows when the next upload attempt is due instead of reporting a problem.
- **Session upload status no longer shows Uploading forever while local history stays busy.** On Linux, macOS and Windows, status reports Needs attention once the local history database has stayed busy for five minutes, or when uploads have been failing for that long, instead of reporting Uploading with a next attempt indefinitely.
- **Windows installers and executables are signed.** On Windows, once the signing account is configured, the Setup program, its uninstaller and every executable and library in the download carry an Authenticode signature (Azure Trusted Signing), so Windows shows a verified publisher instead of an unknown one.
- **Pending session uploads have their own local database.** On macOS, Linux and Windows, upload receipts, retries, exclusions and unresolved batches live in `delivery-queue.db` beside `history.db`. Existing upload state moves with crash recovery and verification before its old tables are removed; unresolved uploads are kept for retry.
- **The macOS menu-bar popup fits its contents after sign-in.** The compact summary no longer sits inside a larger empty panel, and the popup still expands for the signed-out view.
- **Onboarding no longer suggests absent Amp or Capy providers.** On macOS, Linux and Windows, these providers appear only when detected, already selected, or connected. Their setup actions alone no longer make them appear installed; you can still add providers later in Settings.
- **Session uploads say why capture failed instead of "Offline".** On macOS, Linux and Windows, a capture failure (another sync holding the lock, a remote session that cannot be read, a connector sign-in that expired or a connector that is not set up) now shows its own reason, and the upload status stays accurate while delivery is healthy: a connector to sign in to or set up shows "Needs attention", and a failure that is retried shows its reason while records upload.
- **Session search finds sessions by agent name.** On macOS, Linux and Windows, type `@name` (exact) or `@prefix*` (a prefix of at least 3 letters or digits); the agent appears as a chip and the roster offers completions.
- **Enterprise builds stay on their own site.** On macOS, Linux and Windows, a build made for a Cloud site no longer falls back to public Relay servers, and it trusts its own local Relaycast connection.
- **A background provider refresh no longer cancels a Copilot tool call waiting for approval.** On macOS, Agent Relay's periodic provider check no longer cancels a native Copilot call while you decide on "Allow Once" when nothing about the Copilot setup changed, so an approval that takes longer than 30 seconds now completes instead of failing with a generic error. A change to the account, workspace, provider selection, credential or Copilot configuration still cancels it.
- **No more "The request timed out." alert when you open the app.** On iOS, a refresh or conversation read that was still running when the app was suspended no longer shows a timeout alert when you return, nor does one a newer read already replaced or one that was cancelled. A relay that is really unreachable or offline while the app is open still shows the error.
- **Branded installs apply the organization's upload settings from first launch.** On macOS, Linux and Windows alike, a build made for an organization's own site can carry its sharing and upload settings, which apply from the first launch and while offline instead of holding uploads until the site's policy is read. Once read, the site's policy replaces them. Other builds are unchanged.
- **Local service callers for Flows.** Desktop can now give a local runtime such as Flows its own caller identity to start and follow agents on this machine, limited to the harnesses and folders you allow, with its results kept in a private inbox. An allowed folder can't be your home folder or a folder that contains it, and can't be, contain or sit inside Agent Relay's own app data; a spawn into the app data folder is refused. A caller is asked for from the probe and stays pending until you confirm it in Settings. Settings now has a Caller requests section under Account health, on macOS, Linux and Windows, to approve or deny them; this build can't yet confirm it is the signed app, so the section says so and requests stay pending. Signing out deletes every caller. On macOS and Linux the core checks that each call comes from your own user account; on Windows that check is not available yet, so service callers are refused there.
- **Less background CPU when you share more than one Claude Code folder.** On macOS and Linux, history capture keeps one store open for each extra Claude Code folder (a `.claude-<name>` login, or a folder added in Settings) instead of reopening it and rereading the whole session catalog on every capture pass. Selected-session capture likewise keeps its writer open between hydrations. A history database that is replaced or restored is still noticed and reopened. Windows opens them per pass as before.
- **Local history capture uses far less CPU when you are not writing.** On macOS and Linux, while the filesystem watch covers every agent folder, the collector re-checks your whole session history every 30 minutes instead of every minute. New writes, new folders and missed watcher events are still captured right away. Windows keeps the one-minute check.
- **Session uploads wait for ownership where the service asks for it.** On macOS, Linux and Windows, when Cloud enrols a source for session ownership, Relay registers this installation automatically, presents each session's grant with its upload and holds a session's records, without failing the rest, until the session is owned by this installation; the delivery status gives the reason (for example, waiting for ownership). Ownership survives a session reset, and excluding or re-including a session leaves it in place. Sources Cloud has not enrolled upload exactly as before. A sign-in from before session ownership existed lacks it: the status then asks you once to sign in to Agent Relay again to enable session ownership, held sessions wait for that sign-in rather than being refused, and the next sign-in picks them up. Nothing asks you for a key. A session whose owner the service cannot tell is claimed afresh by this installation instead of waiting on an owner that will never appear; if the service refuses that claim too, the session stays held and is not asked about again for an hour.
- **Cleared session launches stay cleared on Windows and Linux.** An older app instance no longer restores a pending launch after another instance confirms it opened or was closed.
- **Native Copilot and legacy VS Code connections no longer share a server name.** On macOS, Linux and Windows, setup keeps native Copilot's `agentrelay` connection separate from legacy VS Code's `relayhistory` HTTP connection, so importing both cannot replace native settings or share one enablement switch. Repair migrates only recognized Agent Relay entries and preserves other servers and hooks.

- **Copilot receives streamed MCP results promptly.** On macOS, Relay's native Copilot connection accepts a completed streamed result as soon as it arrives, so an open response stream no longer hides a successful call or leaves it waiting until timeout. Interrupted or invalid responses remain uncertain and are never retried automatically.
- **Enterprise builds take updates from their own site.** On macOS, Linux and Windows, a build made for a Cloud site's release feed checks for, downloads and installs updates from that site after verifying the feed's signature, the asset size and its checksum, instead of reporting that updates are not read yet. It asks you to sign in when you are signed out and says when the workspace is not entitled to updates. GitHub builds are unchanged.
- **Headless installs for enterprise builds come from their own site.** On Linux and Windows, an enterprise build's `install.sh` and `install.ps1` download the core from its Cloud site's signed release feed, with an install token on a first install or the signed-in core on an update, and check the feed's signature, the size and the checksum before installing. Windows now gets an `install.ps1` made for each enterprise build, as Linux gets `install.sh`. On Linux a first install needs OpenSSL 3 to check the signature and stops without it; on Windows it stops too, unless you pass `-AllowUnverifiedFeed` (or set `AGENT_RELAY_ALLOW_UNVERIFIED_FEED=1`), in which case it warns that the signature check was skipped. Running the command again on Linux starts a stopped core before checking its sign-in. GitHub builds are unchanged.
- **Enterprise builds renew sign-in promptly and remember an up-to-date check.** On macOS, Linux and Windows, a build that reads its site's release feed renews a rejected sign-in, or downloads through the site when the site hands out no download link, as soon as the site answers, instead of waiting for the rest of a slow answer; a slow or broken refusal no longer turns into an unreadable-update error. On macOS, a check that found no newer release still shows as up to date after a relaunch, and the daily check is not repeated early; Linux and Windows already check again shortly after each launch.
- **A build made for its own site stays on that site.** On macOS, Linux and Windows, a build made for its own Agent Relay site no longer falls back to the public Agent Relay hosts. When the site names no valid Relaycast address for the workspace, sign-in and workspace connection show that error instead of connecting to the public Relaycast; the public Agent Relay site and its RelayHistory are no longer trusted beside the build's own site, so session history goes only to the RelayHistory the site names for the workspace and an install saved against the public RelayHistory reports an untrusted history origin. Such a build sends only app-started and sign-in-completed analytics, and only after sign-in, to its own site's analytics gateway, and refuses a PostHog host or key when it is built; it sends nothing to Agent Relay. Builds for agentrelay.com are unchanged.
